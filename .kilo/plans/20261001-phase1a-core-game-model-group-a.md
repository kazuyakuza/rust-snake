### 3.4 `src/game/position.rs`

```rust
pub struct Position {
    pub x: i32,
    pub y: i32,
}
```

- Integer type: **`i32`** (project-wide for coordinates; head movement can transiently compute −1 before the out-of-board check).
- Comparison: **derive equality — no custom code.** Derive line: `#[derive(Debug, Clone, Copy, PartialEq, Eq)]`.
  - `PartialEq` makes "two game objects occupy the same cell" a direct `==` (TODO task 3 requirement).
  - `Copy` because positions are tiny value objects used pervasively without ownership ceremony.
- `x`/`y` are `pub` — encoded exception to the private-members rule, justified because `Position` is a plain value object and forcing accessors on it adds ceremony with zero encapsulation value. Every other type in Group A keeps private fields.
- No methods on `Position` in Group A. Movement offset math (direction → delta) is Group B (task 7) and does NOT belong here.

### 3.5 `src/game/direction.rs`

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Direction {
    Up,
    Down,
    Left,
    Right,
}

impl Direction {
    pub fn opposite(self) -> Direction {
        match self {
            Direction::Up => Direction::Down,
            Direction::Down => Direction::Up,
            Direction::Left => Direction::Right,
            Direction::Right => Direction::Left,
        }
    }
}
```

- Exactly four variants, exact names above (TODO task 3: Up/Down/Left/Right).
- Opposite-detection API (decided): a single method `opposite(self) -> Direction` returning the opposite variant. "Are these two opposites?" is expressed as `candidate == current.opposite()` — Group B uses this in the direction-change rule (task 6). NO second method (`is_opposite_of`, etc.) — one method, chosen here, no alternatives.
- Public by necessity: consumed across modules; the type has no state to encapsulate.

### 3.6 `src/game/snake.rs`

Representation decision (encoded, replaces the global plan's Vec-vs-VecDeque open point): **`Vec<Position>`**, first element = head (brief §14 names `Vec<Position>`; snake max length 40×25=1000 makes Vec's tail-removal cost irrelevant).

```rust
use crate::game::position::Position;

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Snake {
    segments: Vec<Position>,
}

impl Snake {
    pub fn new(segments: Vec<Position>) -> Snake {
        debug_assert!(!segments.is_empty(), "snake must have at least one segment");
        Snake { segments }
    }

    pub fn head(&self) -> Position {
        self.segments[0]
    }

    pub fn segments(&self) -> &[Position] {
        &self.segments
    }

    pub fn length(&self) -> usize {
        self.segments.len()
    }
}
```

- Field `segments` is **private**. First element = head, second element = body/tail front, last element = tail tip. The "head-first" meaning is carried by the API names (`head`, `segments`, `length`) per the self-documenting-code rule — no comments needed.
- `new(segments)` is the single constructor; ownership of the Vec is taken (initial state creation in Group B passes the initial segments). `debug_assert!` catches empty construction in tests; a non-empty snake is a precondition of the domain, so no `Option`/`Result` wrapper is introduced (unreachable in normal flow).
- `head(&self) -> Position` reads `self.segments[0]` (panics only on an empty Vec, prevented by `new`'s debug assert; production path never constructs an empty snake). Copy return since `Position: Copy`.
- `segments(&self) -> &[Position]` gives read-view iteration for collision/food logic later without exposing mutate capabilities.
- `length(&self) -> usize` supports initial-3-segments checks and later scoring/growth tests (Group D).
- No mutation methods (`move`, `grow`, etc.) here — movement (task 7) and growth (task 8) are Group B/C and will be added to this file then.

### 3.7 `src/game/food.rs`

```rust
use crate::game::position::Position;

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Food {
    position: Position,
}

impl Food {
    pub fn new(position: Position) -> Food {
        Food { position }
    }

    pub fn position(&self) -> Position {
        self.position
    }
}
```

- Decision: a one-field newtype wrapper — NOT `pub type Food = Position;`. Rationale: it gives the domain concept a named type (self-documenting), keeps the field private, and leaves a clean expansion point for Group C's placement logic (task 9) without changing any signatures.
- `Food == Food` (derived) suffices for "head == food" tests later; Group C's consumption check reads `food.position()` and compares against `snake.head()` via `Position`'s derived `PartialEq`.

### 3.8 `src/game/state.rs` — game state, game status, board dimensions, playable area

Owns four things (global plan fixes constants + GameState file here; GameStatus lives here too since the global file list has no `game/status.rs`):

```rust
use crate::game::direction::Direction;
use crate::game::food::Food;
use crate::game::position::Position;
use crate::game::snake::Snake;

pub const WIDTH: i32 = 40;
pub const HEIGHT: i32 = 25;

const INITIAL_SCORE: i32 = 0;
```

**Board constants & playable coordinates (TODO task 4):**

- `WIDTH: i32 = 40`, `HEIGHT: i32 = 25` — `pub const`, exact values in cells (not pixels).
- **Playable coordinates (definition, canonical):** `x` is valid when `0 <= x <= WIDTH - 1`; `y` is valid when `0 <= y <= HEIGHT - 1`. The play area is columns `0..=WIDTH-1` and rows `0..=HEIGHT-1`. Outside either is the boundary-loss zone; there is no wrap-around (constraint binding Group C's task 11).
- Typed `i32` (matches `Position`; pulses through boundary math).
- The single-place boundary predicates live here:

```rust
fn is_within_bounds(value: i32, max_inclusive: i32) -> bool {
    value >= MIN_AVAILABLE_COORDINATE && value <= max_inclusive
}
```

with a named constant zero:

```rust
const MIN_AVAILABLE_COORDINATE: i32 = 0;
```

and the canonical public predicate:

```rust
pub fn is_inside_board(position: Position) -> bool {
    is_within_bounds(position.x, WIDTH - 1) && is_within_bounds(position.y, HEIGHT - 1)
}
```

- Single-section boolean conditions rule (encoded resolution): `is`/`if`/**statement** conditions in this phase must reference named predicates only. Conjunctions of already-named predicates inside a function's `return` expression (as above) are permitted — a `return` is not an `if`/`while` statement. If a reviewer objects, the fallback is: split `is_inside_board` into a chained early-return form; either way, never inline `0 <= x && x < WIDTH` arithmetic inside an `if`.
- `WIDTH - 1` / `HEIGHT - 1` written inline is allowed (they are derived from the named constants, not magic numbers).

**Game status (representation only; transitions are Group C's task 13):**

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum GameStatus {
    WaitingToStart,
    Playing,
    GameOver,
}
```

- Group A includes the enum (task 3 lists "game status/state" as a game-state field; determining it in Group A avoids a forced field-add surgery on `GameState` in Group C). NO transition logic, NO display strings here — `WaitingToStart`/`GameOver` screens, terminal messages, and status-change methods are Group C/Phase 1B territory.

**Game state struct & constructor (≤2 args rule applied via parameter object):**

```rust
pub struct GameStateSetup {
    pub snake: Snake,
    pub food: Food,
    pub direction: Direction,
}

#[derive(Debug, Clone)]
pub struct GameState {
    snake: Snake,
    food: Food,
    current_direction: Direction,
    score: i32,
    status: GameStatus,
}

impl GameState {
    pub fn new(setup: GameStateSetup) -> GameState {
        GameState {
            snake: setup.snake,
            food: setup.food,
            current_direction: setup.direction,
            score: INITIAL_SCORE,
            status: GameStatus::WaitingToStart,
        }
    }

    pub fn snake(&self) -> &Snake {
        &self.snake
    }

    pub fn food(&self) -> &Food {
        &self.food
    }

    pub fn current_direction(&self) -> Direction {
        self.current_direction
    }

    pub fn score(&self) -> i32 {
        self.score
    }

    pub fn status(&self) -> GameStatus {
        self.status
    }
}
```

- Name: **`GameState`** (matches TODO task 3's wording; brief §14's `Game` name is not used — the game-object naming settles on GameState).
- All fields **private**; the five accessors are the read API for Groups B/C/D and later phases. No setters in Group A (Group B adds direction-state helpers when implementing task 6).
- Board dimensions: **NOT stored as fields.** The compile-time `WIDTH`/`HEIGHT` consts are the single source of truth for board size (TODO task 4 explicitly demands centralization rather than values scattered anywhere); duplicating them per-instance is unnecessary abstraction (TODO constraint: "avoid creating an elaborate architecture"). If any future multi-board concept appeared, instance fields could be introduced then.
- `GameStateSetup` (public fields) is the mandated ≤2-args parameter object for `new` (rule: max-arguments-per-method — "encapsulate them in a class or object"; staying in `state.rs` is valid since the "new file" phrasing is "when possible", and its shape keeps Group A's file set aligned with the global plan's fixed module list).
- Initial state construction logic (3 non-head segments, direction `Right`, `score = 0`, food placement non-overlapping) is **Group B's task 5** — Group A ships the type + constructor shell only.
- `INITIAL_SCORE = 0` named constant (no magic numbers rule) and initial status is the named variant `GameStatus::WaitingToStart`.
