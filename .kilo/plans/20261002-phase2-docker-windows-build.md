### Technical & Architecture decisions (global)

1. **Target triple: `x86_64-pc-windows-gnu`.**
   - Rationale: it is the only practically cross-compilable Windows target from a Linux Docker container. `x86_64-pc-windows-msvc` requires Microsoft's proprietary `link.exe`/Windows SDK, which cannot run on Linux. The GNU target with the `mingw-w64` GCC linker (available as a Debian/Ubuntu apt package) produces a standard, standalone 64-bit Windows `.exe`.
   - Linker requirement: `mingw-w64` (provides `x86_64-w64-mingw32-gcc`, used as the target linker by Cargo via `~/.cargo/config.toml` `[target.x86_64-pc-windows-gnu] linker = "x86_64-w64-mingw32-gcc"`). Cargo itself installs the target's std libs with `rustup target add x86_64-pc-windows-gnu`.
   - `crossterm 0.29` supports the `windows-gnu` target (its Windows backend uses the WinAPI, which is linked through mingw import libraries); no extra runtime DLLs are needed for this project (only `rand` + `crossterm`, both pure Rust / std).
2. **Toolchain pinning: pin a specific stable Rust minor version** in the `Dockerfile` (e.g. `rust:1.83-slim` style tag — exact current stable tag is decided in the Group A task plan; must be a pinned tag, never `latest`) so the build is reproducible. `rustup`'s `rust-toolchain.toml` is NOT used — the image is the versioning mechanism (single source of truth).
3. **Build flow inside the container:** `cargo build --release --target x86_64-pc-windows-gnu` → copy `target/x86_64-pc-windows-gnu/release/snake.exe` to the host-mounted `dist/` volume as `dist/snake.exe`. The host only sees the final artifact; `target/` stays in the container filesystem (ephemeral) so the host checkout stays clean.
   - `Cargo.lock` will be generated by this build. It SHOULD end up on the host (mount the project root read-write or at least let the lock file be written) — a lockfile is part of reproducibility and the brief lists `Cargo.lock` in §17. Decision: mount the project root read-write, but keep `target/` inside the container via `CARGO_TARGET_DIR=/tmp/target` so only `Cargo.lock` (and nothing else) is written back to the host. Build artifacts (`.exe`) are copied to the mounted `dist/`.
4. **Compose design:** one service `build`, `build:` context `.` with `dockerfile: Dockerfile`, `volumes: [.:/project, ./dist:/out]`, command runs the build + copy. `docker compose run --rm build` is the single command (brief §3).
