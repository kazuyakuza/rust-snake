# Architecture — Rust Snake

**Status:** Phase 2 build infrastructure implemented: `Dockerfile` (pinned `rust:1.98.1-slim-bookworm` + mingw-w64), `compose.yaml` (`build` service → `dist/snake.exe`), `.cargo/config.toml`, and the documentation (`docs/BUILD.md`). The first actual compilation and test execution still await the user's Docker run.

## System Architecture

- Single terminal application; the game state is a logical grid, not pixels (brief §5).
- Two cleanly separated layers: the pure, terminal-free game domain (`src/game/`) is the source of truth for rules; the terminal layer (`src/terminal/`) only reads `GameState`, drives it through the existing domain API, and renders it. `main.rs` composes lifecycle + screens + loop into the runnable flow.

## Core Components

### Domain model (implemented — Phase 1A)

Coded in `src/game/` (brief §14):

- `Position` — `x`, `y` coordinates; `Add` impl for grid arithmetic.
- `Direction` — enum `Up | Down | Left | Right`; `opposite()` and `offset()`.
- `Snake` — ordered head-first `Vec<Position>`; `advance()` with tail-retention flag.
- `Food` — newtype wrapping a `Position`; `occupies()` equality test.
- `GameState` — holds `Snake`, `Food`, `Direction`, score, board dimensions, `GameStatus`; per-tick `advance_one_step()` driver; `start_playing`/`enter_game_over` transitions; canonical playable-bounds predicate.
- Constraint: straightforward Rust, no unnecessary abstraction (brief §14).

### Terminal UI layer (implemented — Phase 1B)

Coded in `src/terminal/`; depends on `crossterm` for the platform handling and reads the domain as `snake::game::*`:

- `Renderer<W: Write>` (`renderer.rs`) — stateless-per-call, full-frame writer: draws border rows (`+`/`-`/`|`), per-cell two-column glyph spans (head `●●` U+25CF×2, body `██` U+2588×2, food `◆◆` U+25C6×2, empty two spaces), and a `Score: N` line, queued at the home position and flushed. Generic over the output so tests can render into a `Vec<u8>` buffer.
- Input (`input.rs`) — pure `map_key_event_to_direction(&KeyEvent) -> Option<Direction>` plus non-blocking `drain_arrow_directions()` / `drain_arrow_event()` built on a zero-duration `crossterm` poll. Reversal rejection is *not* here; it stays in `GameState::change_direction`.
- `TerminalHandle<W: Write>` (`lifecycle.rs`) — RAII guard: `enable()` turns on raw mode, enters the alternate screen, and hides the cursor; `disable()` and `Drop` restore them. Also owns/exposes the output via `output()`.
- `game_loop` (`game_loop.rs`) — `run_playing_loop()` drives the fixed 120 ms loop while the status is `Playing`; a `tick()` helper executes one step headlessly (apply directions → `advance_one_step` → render) for tests.

## Game Loop (implemented — Phase 1B)

`GameState::advance_one_step` advances one step in the domain; the terminal layer adds the timed driver in `src/terminal/game_loop.rs`.

- Fixed tick interval: `TICK_DURATION = 120 ms` per movement (~8.3 moves per second); constant speed; no acceleration (brief §7).
- Per-tick sequence in `run_playing_loop` (loops while `state.status() == Playing`):

1. Record the tick start instant.
2. Drain all buffered arrow directions chronologically.
3. `tick()` — apply each direction via `change_direction` (reversal-rejected in the domain), advance one step (new head, boundary/self collision, food/score/growth/respawn all handled inside the domain), then render the updated state once.
4. Sleep the remainder of the 120 ms tick.

- The loop renders the final (losing) frame, then returns when the status is no longer `Playing`.
- Ordering note: reading input at the head of the tick (rather than the literal brief §7 list) is the deliberate terminal-input accommodation the brief permits ("The implementation can adjust this ordering as necessary").

## Game Layout & Input Rules

- Board: logical grid, `WIDTH = 80`, `HEIGHT = 80` cells (doubled + squared per TODO 2026-10-05); visible ASCII boundaries (`+` corners, `-` horizontal, `|` vertical); no screen wrap (brief §8).
- Cell glyphs (double-width since 2026-10-05, Task 4): each logical cell renders as a two-column span — snake head `●●` (U+25CF ×2), snake body `██` (U+2588 ×2), food `◆◆` (U+25C6 ×2), empty space two spaces; borders stay single-character (`+` corners, `-` ×(2×WIDTH) horizontal rows, `|` verticals); score line rendered as `Score: N` (brief §5, §10, §13).
- Snake starts with 1 head + 2 body segments = 3 blocks; initial direction `RIGHT` (brief §4, §13).
- Controls: arrow keys only; movement is continuous; immediate reversal (e.g. `RIGHT` → `LEFT` in one move) is rejected by `GameState::change_direction` (brief §6).

## Collision & Food Rules

- Head outside the play area → game over; no wrap-around (brief §8, §9).
- Head onto own body segment → game over (brief §8).
- Always exactly one food on the board; spawns randomly, never outside the play area, never on the snake; handles the edge case of no free cells left (brief §9).

## Screens & States (implemented — Phase 1B)

The `GameStatus` enum (`WaitingToStart | Playing | GameOver`) and its transitions live in `src/game/state.rs`. The terminal screens are wired in `src/main.rs`:

- Start screen on launch: `Press any key to start`; gameplay begins after any key press (brief §11). `start_playing()` now has a production caller (the key press in `main`).
- Playing state: the board is re-rendered every 120 ms tick with the score visible as a `Score: N` line (brief §10).
- Game over state: the loop stops and renders the final frame; `show_game_over_screen` prints `GAME OVER`, a blank line, the final `Score: N`, a blank line, and `Press any key to exit`; the application exits on the next key press; no restart system (brief §12).
- All screens clear the full frame (`ClearType::All`) and home the cursor before drawing.

## Design Patterns / Constraints

- Keep-it-simple principle (brief §19): simple Rust → understandable code → successful Windows build → working game.
- Domain/terminal separation: game rules are pure and terminal-free in `src/game/`; only `src/terminal/` and `src/main.rs` touch `crossterm` and the real stdout.
- Generic-over-output rendering (`Renderer<W: Write>`) and a headless `tick()` make the whole loop testable against in-memory buffers without a terminal.
- RAII terminal lifecycle (`TerminalHandle`) guarantees raw-mode/alternate-screen/cursor restoration on both explicit disable and drop.
- No menus/pause/settings/config files — see `brief.md` §16 Non-Goals.

- Build (implemented): `docker compose run --rm build` → host-mounted output `dist/snake.exe`; single command defined in `compose.yaml` (brief §3). Workflow documented in [`docs/BUILD.md`](../../docs/BUILD.md).
