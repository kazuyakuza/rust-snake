# TODO — Phase 1A: Project Foundation & Core Game Model

## Objective

Establish the Rust project structure and implement the core data model and game logic for the Snake game.

This phase focuses exclusively on the **project foundation and game state/logic**. Terminal rendering, interactive keyboard input, the complete game loop, and Docker-based builds are handled in later phases.

The implementation should remain intentionally simple. This is a small Rust learning project, not a production game architecture.

## Tasks

### 1. Initialize the Rust Project [DONE]

Create the basic Cargo project structure for the Snake game.

The project should include:

* `Cargo.toml`
* `src/main.rs`
* Any additional source files only when they provide a clear organizational benefit.

Use standard Cargo conventions and keep the initial project structure minimal.

The project must be designed so that Rust/Cargo does **not** need to be installed in the development environment used by the implementation agent. Do not introduce a workflow that assumes local Rust compilation or execution.

Docker-based compilation is explicitly out of scope for this phase.

### 2. Configure Project Dependencies [DONE]

Define the dependencies required by the core game logic in `Cargo.toml`.

At this stage, only dependencies that are actually needed by the implemented functionality should be introduced.

A random-number generation dependency will be required for food placement.

Do not add a game engine, graphics framework, terminal UI framework, or other unnecessary libraries.

Terminal-specific dependencies should be introduced only when they become necessary in the later terminal/gameplay phase.

### 3. Define the Core Game Types [DONE]

Create the basic types required to represent the game state.

At minimum, the model should provide concepts equivalent to:

#### Position

Represents a cell in the game grid.

```text
x
y
```

The type should make it straightforward to compare positions and determine whether two game objects occupy the same cell.

#### Direction

Represents the four possible movement directions:

```text
Up
Down
Left
Right
```

The implementation should provide the logic necessary to determine whether two directions are opposites.

This will later be used to prevent the Snake from immediately reversing into itself.

#### Snake

Represent the Snake as an ordered collection of positions.

The representation must preserve the distinction between:

* Head
* Body/tail segments

The first element should have a clearly defined meaning, such as representing the head.

#### Food

Represent the food using a `Position`.

#### Game State

Create a simple representation of the overall state required by the game logic.

It should contain, as appropriate:

* Snake
* Food
* Current direction
* Score
* Board dimensions
* Game status/state

Avoid creating an elaborate entity/component architecture.

### 4. Define Board Dimensions [DONE]

The initial game board should use a logical grid of:

```text
WIDTH  = 40
HEIGHT = 25
```

These values represent cells, not terminal pixels.

Keep the board dimensions centralized rather than scattering literal values throughout the game logic.

The playable coordinates should be clearly defined so that boundary collision can be determined consistently.

### 5. Implement the Initial Game State [DONE]

Create the initial game state according to the project specification.

The initial Snake must contain exactly three segments:

```text
2 body segments + 1 head
```

The initial direction should be:

```text
Right
```

The initial score must be:

```text
0
```

The Snake should start at a valid position inside the board.

The initial food must:

* Be inside the playable area.
* Not overlap the Snake.

The exact initial coordinates are an implementation detail, provided they satisfy these constraints.

### 6. Implement Direction Handling [DONE]

Implement the logic required to change the Snake's direction.

The following rule must be enforced:

> The Snake cannot immediately change direction to the direction directly opposite its current direction.

Examples:

```text
Right → Left     invalid
Left  → Right    invalid
Up    → Down     invalid
Down  → Up       invalid
```

Valid changes include:

```text
Right → Up
Right → Down
Left  → Up
Left  → Down
Up    → Left
Up    → Right
Down  → Left
Down  → Right
```

The exact API is an implementation decision, but the rule should live in the game/domain logic rather than being coupled to terminal keyboard handling.

### 7. Implement Snake Movement [DONE]

Implement the core movement operation.

For each movement step:

1. Calculate the next head position based on the current direction.
2. Add the new head position.
3. Move the remaining body segments accordingly.
4. Preserve the current Snake length unless a growth operation is requested.

The movement logic should be independent from terminal rendering and keyboard input.

It should be possible for the game logic to advance one movement step without requiring an interactive terminal.

### 8. Implement Snake Growth [DONE]

Implement a mechanism for increasing the Snake length by one segment.

Growth should follow the normal Snake behavior:

* The new head is added normally.
* The tail is not removed for the movement in which food was consumed.
* As a result, the Snake becomes exactly one segment longer.

For example:

```text
Before eating:

■■●

After eating:

■■■●
```

The implementation should avoid duplicating movement logic specifically for food consumption if a simple `grow`/`should_remove_tail` approach can keep the behavior clear.

### 9. Implement Food Placement [DONE]

Implement logic for generating a valid food position.

The food must:

* Be inside the board.
* Not overlap any Snake segment.

Food placement should use random selection.

The implementation should account for the possibility that a randomly selected position is already occupied by the Snake.

If the board has no free cells remaining, the implementation should handle that situation explicitly rather than entering an infinite loop.

The exact behavior when the entire board is occupied can be kept simple, since this is an edge case outside normal gameplay.

### 10. Implement Food Consumption and Scoring [DONE]

Implement the game logic for determining whether the Snake has consumed the food.

Food is consumed when:

```text
Snake head position == Food position
```

When food is consumed:

* Increase the score by exactly `1`.
* Increase the Snake length by exactly `1`.
* Generate a new valid food position.

The score must start at `0`.

No additional scoring system is required.

### 11. Implement Boundary Collision Detection [DONE]

Implement collision detection against the board boundaries.

The Snake loses when its head moves outside the valid board coordinates.

There must be **no wrap-around behavior**.

For example:

```text
Moving Right
    ↓
Right boundary
    ↓
Game Over
```

Keep collision detection independent from rendering and terminal behavior.

### 12. Implement Self-Collision Detection [DONE]

Implement collision detection between the Snake's head and its body.

The Snake loses when the head occupies the same cell as one of its body segments.

The implementation should account for the normal movement behavior of the tail when determining whether a collision occurs.

The resulting logic should expose a simple way for the game state to determine whether the current movement results in Game Over.

### 13. Define Game State Transitions [DONE]

Introduce the minimum state information necessary to distinguish between the major game states.

At minimum, the game will eventually need to represent:

```text
Waiting to start
Playing
Game Over
```

The terminal UI for these states will be implemented later.

For this phase, only the underlying state representation and transitions required by the game logic need to exist.

Do not implement the terminal messages yet.

### 14. Add Core Logic Tests

Add automated tests for deterministic game logic where practical.

Tests should cover the most important rules, including:

* Initial Snake length.
* Initial score.
* Direction changes.
* Rejection of opposite directions.
* Snake movement.
* Snake growth.
* Food consumption.
* Score increment.
* Food placement constraints.
* Boundary collision.
* Self collision.

Randomized behavior does not need exhaustive testing. Tests should focus on the guarantees the game logic provides.

The tests should not require an interactive terminal.

### 15. Update Readme

Remove base-project notes from the README.
And update the file to specify only details of current project.

## Implementation Constraints

Keep the implementation deliberately small and idiomatic.

Do not introduce:

* A game engine.
* ECS architecture.
* Graphical rendering.
* Terminal rendering.
* Keyboard/input handling.
* Networking.
* Persistence.
* Configuration systems.
* Unnecessary abstractions.

The core game logic should remain independent from terminal-specific concerns.

The implementation should favor readable Rust over premature optimization or sophisticated architecture.

## Out of Scope for This Phase

The following are explicitly deferred:

* Terminal rendering.
* Board visualization.
* Arrow-key input.
* Interactive game loop.
* `Press any key to start`.
* `GAME OVER` terminal UI.
* Terminal cleanup/restoration.
* Docker configuration.
* Windows cross-compilation.
* Windows `.exe` generation.
* Manual Windows validation.

These will be addressed in later phases.

## Expected Result

At the end of Phase 1A, the repository should contain a coherent Rust project with a working and testable **Snake game domain model and core game logic**.

The implementation should be ready for Phase 1B, where the existing game logic will be connected to:

* Terminal rendering.
* Keyboard input.
* A timed game loop.
* Start/game-over interaction.
