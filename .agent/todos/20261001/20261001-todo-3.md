# TODO — Phase 1B: Terminal Game & Gameplay Flow

## Objective

Connect the core Snake game logic implemented in Phase 1A to a simple terminal-based user interface and make the game playable from a console.

This phase focuses on **terminal rendering, keyboard input, the game loop, and the complete gameplay flow**.

The implementation should continue to favor simplicity. No graphical UI, game engine, or advanced terminal framework is required.

## Tasks

### 1. Implement Terminal Rendering [DONE]

Implement a simple terminal renderer for the game board.

The renderer should display:

* The game boundaries.
* The Snake.
* The food.
* The current score.

The board should use the logical dimensions defined in Phase 1A:

```text
WIDTH  = 40
HEIGHT = 25
```

Use simple terminal characters to represent the game elements.

The exact characters are an implementation detail, but the Snake head should be visually distinguishable from its body if practical.

The renderer should redraw the current game state rather than implementing any complex animation system.

Keep rendering logic separate from the core game/domain logic.

### 2. Implement Terminal Input [DONE]

Implement keyboard input for the four arrow keys:

```text
↑
↓
←
→
```

Keyboard input should be translated into the corresponding game `Direction`.

Input handling should integrate with the direction rules already implemented in Phase 1A.

In particular, keyboard input must not allow an immediate reversal of direction.

Terminal-specific input handling should remain separate from the core game logic wherever practical.

### 3. Implement the Game Loop [DONE]

Implement the main gameplay loop.

The Snake should move automatically at a fixed interval of approximately:

```text
120 ms
```

Each iteration of the gameplay loop should:

1. Process available player input.
2. Update the game state.
3. Detect collisions and food consumption.
4. Render the updated state.
5. Wait until the next movement interval.

The exact implementation of timing and input polling is an implementation detail.

The loop should avoid unnecessarily blocking the Snake's movement while waiting for keyboard input.

### 4. Connect Movement, Input, and Game State [DONE]

Integrate the Phase 1A game model with the terminal input and game loop.

The player should be able to:

* Change the Snake's direction using the arrow keys.
* Control the continuously moving Snake.
* Eat food.
* Grow the Snake.
* Increase the score.
* Lose by hitting a boundary.
* Lose by hitting the Snake's own body.

The existing game/domain rules from Phase 1A should remain the source of truth for gameplay behavior.

Do not duplicate collision, movement, scoring, or growth rules inside the terminal/input layer.

### 5. Implement the Start Screen [DONE]

Add the initial game state before gameplay begins.

When the application starts, display a simple message such as:

```text
Press any key to start
```

The Snake should not move while waiting for the player to start the game.

Any key press should transition the game into the playing state.

The exact visual presentation of the start screen is not important as long as the behavior is clear.

### 6. Implement Game Over Flow [DONE]

When the game reaches the Game Over state:

* Stop the game loop.
* Stop Snake movement.
* Display a clear `GAME OVER` message.
* Display the final score.
* Wait for a key press before exiting.

A simple presentation is sufficient:

```text
GAME OVER

Score: 12

Press any key to exit
```

No restart functionality is required.

### 7. Handle Terminal Lifecycle [DONE]

Configure the terminal as necessary to support the game's input and rendering behavior.

The implementation should ensure that the terminal is restored to a normal state when the application exits.

In particular, avoid leaving the terminal with:

* Hidden cursor.
* Unusual input mode.
* Unwanted raw-input behavior.
* Unwanted screen state.

Terminal cleanup should also be considered when the application exits because of an error where practical.

The implementation should remain simple and should not introduce a large terminal abstraction layer.

### 8. Refine Terminal Rendering Behavior [DONE]

Ensure that repeated game updates produce a clean and readable terminal display.

The implementation should avoid unnecessary terminal output that causes the game to continuously scroll.

The board should remain visually stable while the Snake moves.

The exact rendering technique is an implementation detail.

The renderer should prioritize simplicity and reliability over visual polish.

### 9. Validate the Complete Gameplay Flow

Verify that the complete game flow is correctly connected:

```text
Start
  ↓
Press any key
  ↓
Playing
  ↓
Move / Input / Eat / Grow
  ↓
Collision
  ↓
Game Over
  ↓
Press any key
  ↓
Exit
```

The implementation should preserve the rules defined in Phase 1A throughout this flow.

### 10. Add or Update Tests Where Appropriate

Extend the automated test suite only where Phase 1B introduces behavior that can reasonably be tested without an interactive terminal.

Do not attempt to automate full keyboard-driven gameplay.

Existing Phase 1A tests should continue to pass.

Terminal-specific behavior may be validated manually in an appropriate runtime environment.

## Implementation Constraints

Keep the terminal implementation deliberately simple.

Do not introduce:

* A graphical UI.
* A game engine.
* Sprite or texture systems.
* Complex terminal UI layouts.
* Multiplayer.
* Sound.
* Music.
* Persistent high scores.
* Pause functionality.
* Multiple levels.
* Increasing difficulty.
* Power-ups.
* Restart menus.
* Configuration systems unless strictly required by the implementation.

The core game logic from Phase 1A should remain independent from terminal-specific concerns.

The terminal layer should primarily be responsible for:

* Input.
* Rendering.
* Timing.
* Connecting the user interaction to the game model.
* Managing the application lifecycle.

## Out of Scope for This Phase

The following are explicitly deferred:

* Docker configuration.
* Docker image creation.
* Docker Compose configuration.
* Windows cross-compilation.
* Windows `.exe` generation.
* Build automation for Windows.
* Packaging.
* Windows-specific runtime validation.

The build infrastructure will be addressed separately in Phase 2.

## Expected Result

At the end of Phase 1B, the project should contain a complete **terminal-based Snake game** built on top of the core game logic from Phase 1A.

The game should provide:

* A start screen.
* A playable Snake.
* Arrow-key controls.
* Continuous movement.
* Food consumption.
* Snake growth.
* Score tracking.
* Boundary collision.
* Self collision.
* Game Over screen.
* Clean application exit.

The project should now represent a complete functional Snake game, independent of the later Docker-based build infrastructure.
