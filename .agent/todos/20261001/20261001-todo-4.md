# TODO — Phase 2: Windows Build Infrastructure

## Objective

Prepare the project to build the Snake game as a Windows executable using Docker.

The purpose of this phase is to provide a **reproducible build environment and documented build workflow** without requiring Rust to be installed in the development environment.

Docker is used exclusively as the build environment.

The implementation agent is not expected to execute or validate the resulting Windows executable. Manual Windows validation will be performed separately after the build infrastructure is complete.

Docker is not available in implementation context. User will run docker on other context.

## Tasks

### 1. Define the Windows Build Target [DONE]

Determine the appropriate Rust compilation target for the Windows executable.

The project should explicitly document:

* The target triple being used.
* Why the target is appropriate for the intended Windows environment.
* Any relevant compiler or linker requirements.

The selected target should produce a standard Windows `.exe`.

Keep the target configuration explicit and reproducible rather than relying on implicit host defaults.

### 2. Create the Docker Build Image [DONE]

Create a `Dockerfile` containing the environment required to compile the Rust project for Windows.

The image should provide:

* The required Rust toolchain.
* The required Windows Rust target.
* Any compiler/linker dependencies required by that target.
* The tools required to produce the final `.exe`.

The Docker image should contain all build dependencies necessary for the Windows compilation process.

The host development environment should not need a local Rust installation.

Keep the image focused on compilation. Do not add runtime dependencies or unnecessary development tooling.

### 3. Create the Docker Compose Build Workflow [DONE]

Create a `compose.yaml` defining the build workflow.

The Compose configuration should provide a simple build service that:

* Uses the Docker image created for the project.
* Makes the project source available to the container.
* Provides a host-mounted output directory for build artifacts.
* Runs the appropriate Cargo release build command.

The intended workflow should be simple and reproducible, for example:

```text id="c2m6vl"
docker compose run --rm build
```

The exact Compose configuration is an implementation detail.

### 4. Configure the Release Build [DONE]

Configure the Docker build process to generate a release executable.

The build should use Cargo's release profile:

```text id="z8j7qy"
cargo build --release
```

The resulting Windows executable should be made available outside the container.

Use a predictable output location, such as:

```text id="8f4y6m"
dist/snake.exe
```

The final artifact should not depend on the container filesystem after the build completes.

### 5. Handle Build Artifacts [DONE]

Establish a clear convention for generated build artifacts.

The repository should distinguish between:

* Source code.
* Docker/build configuration.
* Generated binaries.

The generated Windows executable should be placed under a dedicated output directory such as:

```text id="f9j4qk"
dist/
```

Generated build artifacts should not be committed to source control.

If appropriate, add the output directory to `.gitignore`.

### 6. Provide a Simple Build Command [DONE]

Ensure there is a single documented command that a developer can use to generate the Windows executable.

For example:

```text id="v5xq8a"
docker compose run --rm build
```

The command should:

1. Start the required Docker environment.
2. Compile the Rust project for Windows.
3. Produce the release `.exe`.
4. Leave the resulting artifact in the expected host directory.
5. Exit cleanly.

Avoid requiring multiple manual Docker commands unless technically necessary.

### 7. Consider Build Script / Cargo Integration Where Useful [DONE]

If a helper script or Cargo-based command can make the build workflow clearer, it may be added.

However, do not introduce a Node.js-style `package.json` workflow.

Use the conventions appropriate to Rust and Docker.

Any helper should remain thin and should ultimately invoke the documented Docker build process.

The host environment should still not require Rust/Cargo to be installed.

### 8. Document the Build Prerequisites

Create or update project documentation describing the requirements for performing the Windows build.

The documentation should clearly state that:

* Rust does not need to be installed on the host.
* Docker is required.
* Docker Compose is required if applicable.
* The build is performed inside the Docker environment.
* The resulting executable is generated for Windows.

The documentation should avoid assuming a specific IDE or development environment.

### 9. Document the Build Workflow

Document the complete build process from a clean project checkout.

The documentation should explain:

1. How to build/start the Docker image.
2. How to invoke the Windows build.
3. Where the generated `.exe` is located.
4. What artifact should be copied or used for Windows testing.

For example:

```text id="jv6y5z"
docker compose run --rm build
```

followed by:

```text id="h9v2wc"
dist/snake.exe
```

The exact commands should reflect the final implementation.

### 10. Update Project Documentation

Update the project documentation to reflect the complete development/build workflow.

The documentation should distinguish between:

```text id="0q5m9p"
Game implementation
        ↓
Rust source code

Windows build
        ↓
Docker
        ↓
Windows .exe

Runtime validation
        ↓
```

Clearly state that Windows runtime validation is a separate manual step and is not part of the Docker build process.

Readme must include a TOC, if not already.

## Ensure Reproducibility

The Docker-based build should be reproducible from a clean project state.

The configuration should explicitly define:

* Rust/toolchain version or appropriate versioning strategy.
* Windows target.
* Build dependencies.
* Build command.
* Artifact location.

Avoid relying on packages or tools being pre-installed on the host.

The goal is that the same repository and Docker configuration can be used to recreate the Windows executable without manually configuring a Rust development environment.

## Implementation Constraints

Keep the build infrastructure deliberately small.

Do not introduce:

* CI/CD pipelines.
* Cloud build services.
* Container orchestration beyond Docker Compose.
* Deployment infrastructure.
* Automatic Windows testing.
* A Windows virtual machine inside Docker.
* Unnecessary build systems.
* Node.js/npm tooling.

Docker should serve one purpose in this project:

> Provide a reproducible environment capable of producing the Windows executable.

## Out of Scope for This Phase

The following are explicitly outside the implementation scope:

* Changes to Snake gameplay.
* New game mechanics.
* New terminal features.
* Windows runtime testing.
* Manual execution of `snake.exe`.
* Testing arrow keys on Windows.
* Visual validation of the terminal game.
* Performance testing of the game.
* Packaging the executable into an installer.
* Code signing.
* Distribution.

The resulting executable will be manually tested by the project owner after the build process has been completed.

## Expected Result

At the end of Phase 2, the repository should contain a reproducible Docker-based Windows build workflow.

A developer with Docker available should be able to execute the documented build command and obtain a Windows executable similar to:

```text id="v5e0l7"
dist/snake.exe
```

No Rust installation should be required on the host.

The resulting executable can then be transferred to a Windows environment for manual validation outside this implementation phase.
